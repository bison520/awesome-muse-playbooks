# 一人三崗：客服＋內容＋調研最小閉環

> 一句話：這個配方是「作戰室」的精簡入門版——幫剛上線、還沒人手的一人公司，用三個分工明確的 agent 每天各跑一輪產草稿，人只花 30 分鐘審核、修改、發布。

- **適合**：產品剛上線，一個人同時回使用者訊息、寫內容、盯市場，每樣都做不深的階段
- **驗證標記**：🔍 改編整理
- **成本量級**：低（三條輕量排程，不需額外付費工具）

## 場景

一個人同時回使用者訊息、寫內容、盯市場，每樣都做不深，還容易漏。

把三件事拆給三個 agent，讓它們每天定時產出草稿，人只花 30 分鐘審核。這是 `war-room.md` 作戰室的精簡入門版：同樣的「agent 產草稿、人做判斷」分工，只是崗位只有三個、交接只靠檔案、還沒有多 agent 並行協作的複雜度。跑順了、需要放大時，再升級到作戰室。

## 輸入

- 客服：過去 24 小時的使用者訊息匯出（信件／表單／社群，**先脫敏**）
- 內容：產品更新日誌、本週想講的 1–2 個主題
- 調研：3–5 個競品名稱、2–3 個產業關鍵詞
- 三條排程的執行時段（建議：調研早上、客服上午、內容下午、人工審核傍晚）

## 步驟

1. **調研 agent**（早上）：按關鍵詞與競品彙整最近 24 小時動態，輸出 5 條要點，寫入 `out/research.md`。
2. **客服 agent**（上午）：把使用者訊息歸類為 bug／需求／諮詢，給每條諮詢寫回覆草稿，寫入 `out/support.md`。
3. **內容 agent**（下午）：讀取前兩步的產出，寫 1 條短文草稿＋1 段更新說明草稿，寫入 `out/content.md`。
4. **人工審核**（傍晚）：改、刪、發。改動多的地方回寫進 prompt，隔天就不用再改一次。

三個 agent 只透過檔案交接（`out/research.md`、`out/support.md`），互不直接呼叫，方便單獨除錯。排程用 Muse 的定時排程即可，不需要額外系統。

## Prompt 範例

調研 agent：

```text
你是 {{產品名}} 的市場調研員。
根據以下資料，列出最近 24 小時與 {{關鍵詞}} 和競品 {{競品列表}} 相關的 5 條要點。
每條：一句結論 + 來源連結 + 對我們的影響（高/中/低）。
沒有可靠來源的內容不要寫，不要編造連結。
```

客服 agent：

```text
你是 {{產品名}} 的客服助理。
把下面的使用者訊息分為 bug / 需求 / 諮詢三類，輸出表格。
對「諮詢」類寫回覆草稿：語氣友善、不承諾上線時間、不編造功能。
不確定的地方標 [需人工]。
輸入訊息已脫敏；輸出也不要出現任何真實信箱或訂單編號。
```

內容 agent：

```text
你是 {{產品名}} 的內容編輯。
參考 research.md 和 support.md，寫：
1. 一條 280 字以內的短文，主題是 {{本週主題}}
2. 一段 150 字以內的更新說明
不要使用誇張詞，不要出現使用者個人資訊。
```

## 產出

虛構範例（AcmeTools 為假名）：

```text
[research] 競品 A 上線了批量匯出；影響：中（附來源連結）
[support]  bug 2 / 需求 3 / 諮詢 5（其中 1 條標 [需人工]）
[content]  短文草稿 1 條，更新說明 1 段
```

## 坑

- **客服訊息沒脫敏就餵給 agent**：信箱、訂單編號別原樣帶進去；先換成佔位再餵，輸出的草稿也不要回填真實資訊。
- **調研 agent 編造來源**：它很愛寫看起來很真的連結。prompt 寫死「無來源不寫」，審核時抽查連結能不能開。
- **三步串行，前一步失敗後面會空跑**：每一步開始前先檢查輸入檔是否存在；缺檔就跳過本輪並標記，不要讓後面拿空檔案硬寫。
- **內容 agent 用誇張詞**：一人公司的內容經不起「最強」「第一」這種詞；prompt 明確禁用，審核時第一眼就看這個。
- **改動不回寫 prompt**：同樣的修改每天重做一次，等於沒省時間。改動多的地方當天就回寫進 prompt。
