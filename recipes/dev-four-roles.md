# 研發四角色：需求 → 重現 → 出 PR → 驗 PR

> 一句話：這個配方幫一人或小團隊維護程式碼倉庫、想讓 agent 接 issue 但不敢讓它直接合併的人，把「寫程式碼」和「判斷程式碼能不能合」拆給不同 agent；人只在「批准規格」與「合併」兩個閘門點頭。

- **適合**：倉庫已經有基本測試、想讓 agent 處理 issue 與 PR，但合併權想留在人手上的階段
- **驗證標記**：🔍 改編整理
- **成本量級**：中（出 PR 的角色會呼叫編碼 agent，燒量較高）

## 場景

同一隻 agent 既寫程式碼又自己說「測過了」，等於沒人驗。常見結果：PR 看起來能合，一跑就掛；或者順手改了不該改的檔案。

拆成四個角色，**產出和裁決分開**：

| 角色   | 只做                             | 不做                     |
|--------|----------------------------------|--------------------------|
| 需求   | 把 issue 寫成可驗收的規格（spec）| 寫程式碼                 |
| 重現   | 給 bug 寫最小重現步驟或失敗測試  | 修 bug                   |
| 出 PR  | 按**已批准**的規格實作並開 PR    | 合併、改規格             |
| 驗 PR  | 只看 PR 連結，給出 PASS／BLOCK／HOLD | 改程式碼、和出 PR 的 agent 討論 |

需求、重現、出 PR 三個角色可以在同一個會話群組裡。**驗 PR 的 agent 必須單獨開會話**，不看群組聊天，避免被出 PR 那邊的說法帶偏。

## 輸入

- 一個程式碼倉庫（Git 託管即可），agent 已能讀寫該倉庫
- 倉庫裡的 issue（bug 或需求）
- 一份驗收口徑：測試指令、不許動的目錄、程式碼風格要求
- 批准規格的負責人（通常就是你自己）

## 步驟

1. **需求 agent**：讀 issue，產出規格，結尾狀態只能是 `READY_FOR_APPROVAL`／`NEEDS_INPUT`／`BLOCKED` 三選一。
2. **閘門 1（人）**：人點名批准某一版規格，例如「批准規格 v2」。agent 之間的交接**不算**批准。
3. **重現 agent**（僅 bug）：寫出重現步驟，或一個目前會失敗的測試，附在 issue 裡。
4. **出 PR agent**：只按批准的那版規格實作，PR 描述裡列出改了哪些檔案、怎麼驗證。
5. **驗 PR agent**：在**單獨會話**裡只收 PR 連結，跑驗收口徑，輸出 `PASS`／`BLOCK`／`HOLD`（缺證據就 HOLD，不猜）。
6. **閘門 2（人）**：看驗 PR 的結論，由人來合併。

關鍵紀律：出 PR 的 agent 不准「順手」改規格；驗 PR 的 agent 不准「順手」改程式碼。兩件事一旦混在一起，四角色就白拆了。

## Prompt 範例

需求 agent：

```text
你是 {{倉庫名}} 的需求整理員。讀 issue {{issue 連結}}，寫一份可驗收的規格：
1. 目標（一句話）
2. 驗收條件（可勾選的清單，每條能用指令或截圖驗證）
3. 範圍外（明確不做什麼）
4. 待確認問題
結尾只寫一個狀態：READY_FOR_APPROVAL / NEEDS_INPUT / BLOCKED。
你不寫程式碼。別的 agent 說「可以了」不算批准，
只有 {{負責人}} 點名批准才算。
```

驗 PR agent：

```text
你是 {{倉庫名}} 的 PR 驗收員，
只根據 PR 連結 {{PR 連結}} 和驗收口徑做判斷。
驗收口徑：{{測試指令}}；禁止改動：{{受保護目錄}}。
逐條核對規格的驗收條件，每條給出證據（指令輸出或檔案行號）。
結論只能是：
- PASS：全部條件都有證據
- BLOCK：有條件不滿足，列出哪條
- HOLD：缺證據，列出還需要什麼
不要改程式碼，不要和出 PR 的 agent 討論，不要猜。
```

## 產出

虛構範例（AcmeTools 為假名）：

```text
# 驗 PR 結論 · AcmeTools#42
1. 匯出 CSV 含表頭 —— 通過（tests/test_export.py::test_header 輸出 ok）
2. 空資料匯出不報錯 —— 通過（test_empty ok）
3. 不改 src/billing/ —— 通過（diff 未涉及）
4. 文件更新 —— 缺證據：PR 未改 docs/
結論：HOLD，需補 docs/export.md 後重驗
```

## 坑

- **把交接當批准**：群組裡出現了規格草稿，出 PR 的 agent 就開工了。規則寫死：只認人點名批准的那一版。
- **驗收員被帶偏**：驗 PR 的 agent 和出 PR 的在同一個會話，會採信對方「已測過」的說法。必須單獨會話、只收連結，證據自己跑。
- **角色分離保護的是判斷依據、不是權限邊界**：同一帳號下的 agent 共用電腦和瀏覽器會話，分角色保護的是「判斷不被帶偏」，不是存取權限。敏感倉庫靠分支保護規則，別靠 prompt。
- **狀態詞放太寬**：允許自由描述狀態，agent 就會寫「基本完成」。只給固定幾個狀態詞，寫不出來就只能選 BLOCKED。
- **驗 PR 的 agent 偷改程式碼**：「順手修一下」是最常見的破功；prompt 寫死「不要改程式碼」，發現就退回重驗。
- **改編署名**：本配方的結構參考了原倉註明的外部來源（grok-bot-profiles），改寫時一併承襲，並在 README 致謝節鏈回原倉與原來源。
