# 出海客服：多語言工單先分流、只出草稿

> 一句話：這個配方幫剛開始接到英文／多語言諮詢、還請不起專職客服的一人公司，把工單先脫敏、分流，再產出回覆草稿；付款、安全、法律類一律轉人工，agent 永遠不直接發信。

- **適合**：產品剛開始有海外使用者、工單語言混雜（英文為主，偶有西語／日語等），一個人既要判斷優先順序又要寫得體回覆、容易漏單或過度承諾的階段
- **驗證標記**：🔍 改編整理
- **成本量級**：低（只用既有的 agent 與文件，不需額外付費工具）

## 場景

工單語言混雜，一個人回不完；回覆寫得太慢怕得罪使用者，寫得太快又怕承諾了沒上線的功能。配方把流程拆成：**脫敏導入 → 語言／類型分流 → 草稿 → 人工閘門**。agent **不直接發信**；寄出去的每一封，都由人親自點確認。

這條路線和 `one-person-three-roles.md` 的客服崗是互補的：那裡是「一人三崗日閉環」裡的客服輪次，這裡是專門處理多語言工單的分流與回覆草稿。

## 輸入

- 過去一段時間的工單匯出（信件／表單／幫助台），**先脫敏**：去掉真實信箱、訂單編號、地址、可識別姓名
- 產品事實卡：`{{產品名}}`、已上線功能清單、已知限制、退款／服務水準（SLA）政策摘要（只寫對外可公開的條款要點）
- 支援的回覆語言：`{{預設回覆語言}}`（例如 English）；選填 `{{可翻譯語言列表}}`
- 升級規則：涉及付款爭議、安全、法律、媒體 → 一律 `[需人工]`，不產生可寄出的草稿
- 幫助台原單的編號規則（用來對齊分流表 ID）

## 步驟

1. **導入脫敏**：把工單貼上或寫入 `inbox/tickets-{{日期}}.md`；真實聯絡方式留在幫助台，不進 agent 上下文。
2. **分流**：agent 輸出表格——語言、類型（bug／需求／諮詢／投訴／其他）、優先順序（高／中／低）、是否可自動出草稿。
3. **草稿**：只對「諮詢／低優先順序的需求說明」寫回覆草稿；語氣克制，不承諾未上線功能與具體上線時間。
4. **翻譯（選填）**：若使用者非英文，先出英文草稿 → 再譯成目標語言；關鍵條款以英文事實卡為準。
5. **人工閘門**：人在幫助台核對收件人與原文後，複製草稿寄出或手動修改；高優先順序與 `[需人工]` 條目當天必須人看。
6. **回寫**：反覆改過的句子沉澱進事實卡或 prompt，減少下次幻覺。

## Prompt 範例

分流＋草稿（可拆給兩個 agent，這裡合併示範）：

```text
你是 {{產品名}} 的出海客服助理（只寫草稿，不寄信）。
輸入是已脫敏的工單列表。請輸出：

1) 分流表（Markdown 表格）：
| 編號 | 語言 | 類型(bug/需求/諮詢/投訴/其他) | 優先順序(高/中/低) | 可出草稿?(是/否) | 理由 |

2) 對「可出草稿=是」的每條，寫回覆草稿：
- 預設語言：{{預設回覆語言}}
- 語氣：友善、簡潔、不賣弄
- 只陳述事實卡內已有的資訊；不確定就寫 [需人工]
- 禁止：承諾上線時間、編造功能、提及內部路徑、索取密碼或驗證碼、寫入真實信箱或訂單編號

3) 「需人工」清單：付款／退款爭議、安全、法律、媒體、情緒激烈、事實卡未涵蓋的問題。

事實卡：
{{產品事實卡}}

工單：
{{脫敏工單正文}}
```

人工閘門檢查清單（給人看的，寄出前逐條勾）：

```text
[ ] 收件人與工單原文來自幫助台，不是 agent 上下文裡的地址
[ ] 草稿未承諾未上線功能或具體日期
[ ] 無金鑰 / 內部路徑 / 其他使用者資訊外洩
[ ] 高優先順序與投訴類已由人處理或明確延期
```

## 產出

虛構範例（AcmeTools 為假名）：

```text
# out/support-2026-10-18.md
| 編號 | 語言 | 類型 | 優先順序 | 可出草稿? | 理由 |
| T1 | en | 諮詢 | 低 | 是 | 問批量匯出是否支援 CSV |
| T2 | en | 投訴 | 高 | 否 | 涉及付款，需人工 |
| T3 | es | 諮詢 | 中 | 是 | 問時區顯示，可譯 |

草稿 T1（English）：
Thanks for reaching out. AcmeTools currently exports CSV from the Orders view
as described in our docs. If you need another format, tell us which one—
we track requests but can't commit to a date. [需人工: 是否附文件連結]

需人工：T2 付款爭議 → 回幫助台原單處理
```

## 坑

- **未脫敏就餵模型**：真實信箱、訂單編號、姓名會進上下文甚至日誌；導入前一律先換成 `{{使用者稱呼}}`／`{{工單編號}}`。
- **agent 直接發信**：最危險。即使連接器能寄信，也要經過人工閘門；本配方預設「只出草稿」，寄出動作永遠是人做的。
- **過度承諾**：模型愛寫「我們下週就修好」；prompt 禁止具體日期，政策範圍外的請求一律 `[需人工]`。
- **多語言事實不一致**：先定英文事實卡，再翻譯；不要讓模型用目標語言「自由發揮」政策內容。
- **工單編號混亂**：分流表編號與幫助台編號對不上，人會回錯單；約定編號前綴，或只用幫助台編號的雜湊佔位。
- **和一人三崗的客服崗重複**：本配方專注出海多語言分流與閘門；更粗的三角色日閉環見 `one-person-three-roles.md`，兩條路線不要混成一團。
