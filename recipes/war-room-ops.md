# 作戰室實戰版：PM 統籌多個 agent 的任務書派工制

> 一個人當 PM，指揮雲端主力 agent＋雜務型 agent 24 小時接力：任務書寫死驗收標準，agent 寫 REPORT 回報，你只看結果點頭。

- **適合**：手上有 2 個以上 agent（雲端常駐＋本機），想讓它們半夜自己幹活、早上只驗收的人
- **驗證標記**：✅ 真機跑通
- **成本量級**：低

## 場景

一個 agent 什麼都做，很快變成瓶頸；多個 agent 又容易各做各的、回報格式不一、你半夜還要起來救火。解法是把你自己定位成 PM：只寫任務書、只看 REPORT 驗收，不跳進去執行。

角色分工建議：

| 角色 | 個性 | 適合的任務 |
|---|---|---|
| 主力 agent（雲端 24 小時在線） | 快、什麼都接 | 社群上稿、網站更新、日常雷達 |
| 雜務型 agent | 慢約三倍、但返修率低 | 高品質任務：商品化、核心邏輯、一次要做對的事 |
| 快槍手 | 速度最快、完成度打七折 | 趕時間的初稿、大量嘗試性任務（逐項實測驗收） |

## 輸入

- agent 清單與分工（誰是主力、誰是雜務型）
- 共用資料夾：`<共用資料夾>/warroom/tasks/`（任務書）、`<共用資料夾>/warroom/reports/`（回報區）
- 任務書範本（見下方 Prompt 範例）
- REPORT 命名規範：`REPORT-<任務編號>-<日期>-<agent名>.md`
- 已處理回報清單：`reports_seen.log`（判新回報用全檔比對，不要只看尾部）

## 步驟

1. **寫任務書**：一份 Markdown，包含：背景一句話、要做的事（編號列出）、驗收標準（寫死、用結果說話，例如「輸出檔案存在且可開啟」「清單新增一批次」）、產出路徑（絕對路徑）、執行方式（背景執行、log 位置）。驗收標準是黑箱的：不管 agent 怎麼做，只看結果。
2. **派工**：把任務書放進任務書資料夾，並在 agent 的排程器建一個單次任務去執行它。**注意：只放資料夾不會自動觸發**——一定要有「掃任務資料夾」的常駐排程，或手動建單次任務。建單次任務時，確認排程器的重複次數設為 1 次，不要建成無限循環。
3. **執行**：agent 照任務書跑，全程背景執行，log 寫到約定位置。任務書裡寫明：中途被打斷要能從 log 接著查，不要重頭來。
4. **寫 REPORT**：agent 完成後在回報區寫 REPORT，格式固定：做了什麼、產出在哪（絕對路徑）、驗收標準逐條對照（通過／未通過）、需要人決策的事。
5. **三方驗收**：PM 用三個獨立證據驗收——①排程器的執行紀錄顯示成功 ②產出檔案真的存在且打得開 ③下游清單／批次真的有新增。三個對得上才算完成，缺一個就打回。
6. **結案**：驗收通過後，把 REPORT 檔名寫入 `reports_seen.log`，任務書歸檔。

## Prompt 範例

任務書範本（每次派工複製一份填空）：

```text
# 任務書 <任務編號>：<一句話標題>

## 背景
<為什麼要做這件事，一句話>

## 要做的事
1. <具體事項一，含絕對路徑>
2. <具體事項二>
3. <…>

## 執行方式
- 背景執行，log 寫到 <log 路徑>
- 遇到需要人決策的點：停下來寫進 REPORT，不要自己猜

## 驗收標準（黑箱，只看結果）
- [ ] <產出檔案> 存在且可正常開啟
- [ ] <下游清單> 新增一批次，數量為 <N>
- [ ] 排程器執行紀錄為成功

## 回報
完成後在 <回報區> 寫 REPORT-<任務編號>-<日期>-<你的代號>.md，
格式：做了什麼／產出路徑／驗收逐條對照／需決策事項。
```

## 產出

虛構範例：

```text
# REPORT-TASK-042-2026-10-21-scout.md

## 做了什麼
按任務書抓回 12 個候選連結，去重後剩 9 個，已寫入候選清單。

## 產出路徑
<共用資料夾>/warroom/out/candidates-2026-10-21.md

## 驗收對照
- [x] 產出檔案存在且可開啟
- [x] 候選清單新增一批次（9 筆）
- [x] 排程器執行紀錄為成功

## 需決策
其中 2 筆來源可信度為「中」，是否納入明天的上稿排程，請 PM 定奪。
```

## 坑

- **任務書放了沒人撿**：共用資料夾不會自己觸發 agent。派工＝放任務書＋建排程任務，兩步缺一不可。
- **觸發端斷線連帶失敗**：用 SSH 下指令觸發雲端任務時，指令若中途被斷線殺掉，該次執行會被記為「不明中斷」。補救：用完全脫離連線的方式觸發（nohup 背景化），事後用三方驗收確認。
- **回報判重只看尾部**：已處理的 REPORT 可能沉在紀錄檔中段。判新回報要用全檔比對，不要只看最後幾行，否則會重複處理。
- **agent 的「完成了」打折扣**：快槍手型 agent 的「已完成」先打七折看，三方驗收就是為此設計的。驗收標準寫得越具體（檔案存在、數量對得上），折扣越小。
- **第三方服務偶發錯誤**：發布時遇到連線被重置，不代表失敗——先去查對方系統裡到底有沒有成功，確認沒有才重發，否則會重複發布。
- **通用版作戰室見 `war-room.md`**：那篇講分工與文件交接的方法論，這篇是我們實際跑的派工與驗收血淚。
